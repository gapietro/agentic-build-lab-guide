                                                        Agentic Build Lab

                                                        How this lab works · 5 minutes to read

                                                        In one day you build a small ServiceNow app, Priority Guard: a priority floor for incidents on critical services. Claude Code writes the code. You make the decisions, and checks decide whether work may go on.

                                                        The app isn't the point. The method is: the AI types, people and checks decide. Every module has one catch, a moment where the process stops a mistake. Those moments are the lesson.

                                                        Rules for the whole lab

                                                        1. Never paste this guide into Claude. Only the text in 🤖 boxes goes in. If Claude sees the checks, they stop being checks.
                                                        2. Passwords go into your own terminal or browser, never into Claude.
                                                        3. Claude never runs now-sdk auth. You install the app yourself. The only installs Claude runs are the grade's, to lab-pdi.
                                                        4. Never use a production instance.
                                                        5. Trust what a command prints, not what Claude says about it.
                                                        6. Follow what really happens. Don't re-run a prompt to get a nicer answer. Write down what happened, and carry on.

                                                        When Claude asks permission, read the command, then:

                                                        • 1. Yes for git, gh, npm, node and now-sdk build, and for files in ~/projects/priority-guard or the kit's copy, ~/projects/prove-it-kit.
                                                        • No for now-sdk auth, now-sdk install, anything that names your instance, and anything in this guide's folder.
                                                        • Not sure? No, then ask Claude what it was for.
                                                        • Never choose "Yes, and don't ask again". The asking is the check.

                                                        Words you'll meet

                                                        • Repo: a folder whose history git keeps. Your app's repo is ~/projects/priority-guard/app.
                                                        • Commit: one saved snapshot in that history.
                                                        • Branch: a separate line of commits. main changes only through pull requests.
                                                        • Pull request: a request on GitHub to merge a branch into main. It's reviewed first.
                                                        • Story: one small piece of work, filed as a GitHub issue.
                                                        • Gate: a milestone that stories hold up: MERGE, INSTALL, DEMO, HANDOFF.
                                                        • Design term: one numbered rule in your design record, such as C3. Every test names the term it proves.
                                                        • Catch: a real problem the process found and that got fixed, or that changed a decision. A check firing on something you planted to test it isn't a catch.

                                                        Some steps ask for one exact word, such as confirmed or ship it. Type it exactly as shown, on its own.

                                                        5. Finishing the slice

                                                        The gates, in order

                                                        Why this step: The open-story count shows where you really are, so nobody has to guess.

                                                        The plan files one milestone per gate: MERGE → INSTALL → DEMO → HANDOFF. The next gate is the one BACKLOG.md names at the top. Count what stands in its way, swapping in its name. 🔍 Check:

                                                        Run exactly this and show me the raw output, unedited: gh issue list --state open --label "gate:<next gate>" --limit 5000 --json labels --jq '[.[] | select(all(.labels[]; .name != "register"))] | length'

                                                        Keep running the build loop, one story at a time, until it's zero. Then move to the next gate. Nothing closes milestones for you. The count is the truth.

                                                        Evidence the grade needs

                                                        Why this step: The grade credits only what it can see proof of, so leave the proof where it looks.

                                                        • DEMO counts only if the DEMO story is closed with a comment that records who saw what, live, as which user, and when.
                                                        • Demo data must be seeded as source in src/.
                                                        • Every design term must be named by a test (C<n>: …), including the off switch.

                                                        The order to finish

                                                        Why this step: Grading before the handoff finds problems while they're still cheap to fix.

                                                        1. Close every gate up to and including DEMO.
                                                        2. Grade at DEMO, for real. That's Module 8's after-the-workshop real grade: Part A again, choosing DEMO, merged on the branch chore/grade-demo. It isn't a preview, because the milestone is reached.
                                                        3. The grade files its findings as stories. Some may re-open an earlier gate. Work them until every gate up to DEMO is back to zero.
                                                        4. Hand off: Module 8 Parts B and C, including the drill and the verdict.
                                                        5. Grade again at HANDOFF. That's the grade PROMOTE.md asks for.

                                                        Done means

                                                        Why this step: A clear finish line stops the slice dragging on, or being called done too soon.

                                                        • ☐ Every gate's count is zero: BACKLOG.md names no next gate.
                                                        • ☐ The app is installed on your development instance, and your live check passes as your ordinary user.
                                                        • ☐ The DEMO story is closed with the owner's live sign-off recorded.
                                                        • ☐ A real grade at HANDOFF, not a preview.
                                                        • ☐ HANDOFF.md has a verdict.

                                                        Check-ins with your instructor

                                                        Why this step: A second pair of eyes spots a stuck slice before a week is lost.

                                                        When Bring The question
                                                        End of week 1 SLICE.md, the board, your catch list Is the count going down? If it's flat for a week, stop filing and start closing.
                                                        End of week 2 Both grades, HANDOFF.md Is it done? What's next: the next slice, or production?

                                                        If the slice won't finish

                                                        Why this step: Cutting the wrong way loses work or lowers the grade; this way keeps everything on record.

                                                        Cut stories, not terms. In the next /prove-it:build-plan preview, mark each cut story as register, keeping its existing key. That takes it off the gates without losing it.

                                                        Avoid withdrawing a design term. The kit never deletes terms: a withdrawn term stays in the record, and as far as the kit's documents say, it still needs a test. Without one, the grade is capped at 74. That's why the slice should be small from the start.

                                                        Getting it to production

                                                        Lab home · ← Your own PRD track

                                                        Everything in this lab runs on a development instance, on purpose. The coding agent never touches test or production, and nothing in the kit does either. Getting a finished app to production goes through the customer's own change process, run by the people who own those instances.

                                                        This page is a checklist for that step, not a set of commands. How apps move between instances (an application repository, source control, or something else) is the customer's platform team's decision, and it differs from customer to customer. Several platform behaviours below are marked confirm with your platform team: they're likely, but check them on their instances before you rely on them.

                                                        1. The bar before you ask

                                                        None of these can be waived.

                                                        • ☐ The slice is done, as OWN-PRD.md section 5 defines it: every gate's count is zero, and BACKLOG.md names no next gate.
                                                        • ☐ A real grade at HANDOFF, not a preview, in the "ready with named fixes" band (75) or above.
                                                        • ☐ No cap on that grade from build, tests or the secrets scan, from a missing signature, or from an unbounded AI feature.
                                                        • ☐ HANDOFF.md says READY. NOT READY means someone else couldn't run the app from the runbook. That's not something to accept on paper.
                                                        • ☐ The real owner has seen it work live as an ordinary user. The DEMO story is closed with that recorded.
                                                        • ☐ The app has an off switch: an admin-controlled setting, in the design as a term, with a test, that turns off the app's logic. And the runbook's Recovery section names it. Plain-code logic is live the moment it's installed. Without a switch, the only way to stop it is to back the whole app out.

                                                        What can be accepted: a test-coverage gap or a runbook gap the grade named, if the real owner accepts it in writing. Record it in docs/PROMOTION.md (section 2), with who accepted it, when, and the date it will be closed.

                                                        2. Agree how it moves

                                                        Meet the customer's platform team before you raise anything, and write their answers in the repo, in docs/PROMOTION.md (admit it with an allow line, as you did for docs/):

                                                        1. The delivery mechanism. How a scoped app moves from development to test to production at this customer. Ask them, don't assume.
                                                        2. Who installs. On test and production it's their team. Never the coding agent, and ideally not the builder either.
                                                        3. Global and shared changes. Anything the app changes outside its own scope: shared tables, global rules. These are in your LLD §2–§3, and usually need their own approval.
                                                        4. Cross-scope access. On a development instance the platform may record cross-scope access for you as the app runs. On test and production it may not. Logic that worked on dev then fails. Confirm with your platform team, and make sure every cross-scope privilege the app needs is declared in source (your LLD §4 lists them).
                                                        5. Demo data stays out of production. Your seed records are part of the app's source, so they'd install everywhere. Agree how they're excluded from the production install, and confirm it works on test.
                                                        6. Per-instance configuration. Role-to-group assignments, setting values, and any integration's endpoint and credential are different on each instance. They're set by an admin, by hand, from the runbook's configuration steps. List them.
                                                        7. Back-out. How to remove the app if switching it off isn't enough, and what that costs. Uninstalling a scoped app may delete its tables and the data in them, such as override records or audit rows. Confirm with your platform team. Write the agreed back-out in docs/PROMOTION.md.
                                                        8. The version. Bump the app's version in now.config.json, merge it, then tag that commit, so test and production get exactly what was graded:
                                                          git tag -a v1.0.0 -m "Slice 1: <what a user can now do>"
git push origin v1.0.0
                                                          If anything changes after the HANDOFF grade (runbook fixes, the version bump), grade again at the tagged commit.

                                                        3. Test, with the runbook only

                                                        1. The platform team installs the tagged version on test, following RUNBOOK.md and nothing else, then does the per-instance configuration (section 2, item 6). If they need to ask you anything, that's a gap in the runbook: fix it through the build loop, re-tag, and start this step again.
                                                        2. First contact with real data. Test usually holds copies of real records. Re-run your live check, and the access checks, as ordinary users. Check the cross-scope access works here. Anything that fails goes back through the build loop on development. Never a fix on test.
                                                        3. Rehearse Recovery on test. Switch the app off with its off switch, and check it really stops. Then switch it back on. If the platform team allows it, rehearse the agreed back-out too. The handoff drill tested diagnosis, not recovery, so this is new evidence.
                                                        4. Re-run the handoff drill on test, if the platform team allows a planted failure there.

                                                        ✅ Check: every result is in docs/PROMOTION.md, with dates and who ran it. Nothing was fixed on test by hand.

                                                        4. The change request

                                                        Raise it through the customer's change process. Attach the evidence. Don't summarise it:

                                                        Evidence From
                                                        What changes, and what doesn't The signed design record, and LLD §1
                                                        How well it's built GRADE.md, graded at the tagged commit
                                                        Whether someone else can run it HANDOFF.md and RUNBOOK.md
                                                        What was tested on test, and by whom docs/PROMOTION.md
                                                        How to switch it off, and how to back it out The runbook's Recovery section, and the back-out in docs/PROMOTION.md, rehearsed on test
                                                        Anything accepted rather than fixed docs/PROMOTION.md, with the owner's written acceptance

                                                        Say what isn't done. List the deferred capabilities from SLICE.md in the change request itself. Approvers should never discover a gap after go-live.

                                                        5. Production

                                                        1. Their team installs the same tag from the runbook, without the demo data, then does the per-instance configuration.
                                                        2. The off switch starts off. The app is installed, but its logic doesn't run yet.
                                                        3. The owner switches it on, at an agreed time, with you available.
                                                        4. Watch the first day. Use the checks the runbook gives an on-call person: the platform's own screens, and the app's own lists and logs.
                                                        5. If it misbehaves: switch it off first, then diagnose, from the runbook. Back out only if switching it off isn't enough, and only as agreed in docs/PROMOTION.md.

                                                        ✅ Done when: it's on in production, the first day's checks are clean and written down, and the owner has signed off in the change request.

                                                        6. After go-live

                                                        • The next slice extends the same design: see OWN-PRD.md section 6. It goes back through the design challenge before any code.
                                                        • Anything found in production becomes a story on the board, built through the loop on development, then promoted with this page again. Never a hand fix in production.

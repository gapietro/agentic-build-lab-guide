                                                                                          Agentic Build Lab — build a ServiceNow app with a coding agent, and prove it works

                                                                                          A hands-on workshop. In three days you build a small ServiceNow app, Priority Guard, the way real work arrives: from a use case, workshop notes and technical notes, through a PRD and an LLD, to a reviewed, installed, handed-over app. A coding agent (Claude Code) does the typing. You make the decisions, and checks decide whether each piece of work may go on.

                                                                                          You're not here to learn this app. You're here to learn the method, so you can use it on your own work next week. Every module has a moment where the process catches something. Those moments are the lesson.

                                                                                          Read it online: https://claude.ai/artifact/LLZPgYakMRU9hWxmhughrQ (the same guide as one page, with a menu on the left; your instructor shares the link with you). You still clone the guide in Module 0: the steps copy files from it.

                                                                                          The one idea: the AI does the typing. People and checks do the deciding.

                                                                                          The path, and the document each step leaves:

                                                                                          Inputs → PRD → Consult → Research and LLD → Challenge and sign → Plan → Build → Grade and handoff
                                                                                          Use case, workshop notes (tech notes join at research) Accepted PRD CONSULT.md Signed LLD Signed design record The board Merged, installed code GRADE.md, RUNBOOK.md, a verdict

                                                                                          4. Three rules for the whole lab

                                                                                          1. The guide is your checklist, not the agent's instructions. Never paste this guide into Claude. The kit and Claude do the work; you check it. If Claude sees the checks, they stop being checks.

                                                                                          2. Two folders, never mixed.

                                                                                          Folder What's in it Does Claude see it?
                                                                                          ~/projects/priority-guard/ Your workspace: the accepted PRD, the consult, the customer's notes, then your app's repo Yes. Run Claude here.
                                                                                          ~/projects/priority-guard-notes/ Your notes: your log and your catch list Never

                                                                                          3. Follow what really happens. Claude won't word things the way this guide does. The checks describe what a good result looks like, not exact words. If what you see is different, don't re-run the prompt to get a "better" answer. Write down what happened, and carry on or ask your instructor.

                                                                                          5. Words you'll type

                                                                                          Some steps ask for one word. Type it exactly. The kit and your project instructions watch for these words.

                                                                                          You type When What happens
                                                                                          confirmed Module 2, after the consult restates the brief The consult starts
                                                                                          Confirmed. Module 4, after the design challenge reads back the terms It writes exactly those terms
                                                                                          Not agreed yet. Module 4, after a read-back you don't accept It asks for your correction
                                                                                          approve, then dry run, then apply Module 5, after the plan preview Shows, then files, the plan on GitHub
                                                                                          approve, then Dry run first., then apply Module 8, after the grade's findings Shows, then files, the findings as stories
                                                                                          Take the top one. Module 6, after the session open Starts whatever is really at the top, not the story you expected
                                                                                          confirm Modules 5–8, after Claude proposes something Accepts it (for example, a story's five bullets)
                                                                                          ship it Modules 5–8 Push, open a pull request, review, fix once, merge when green

                                                                                          Gates. The kit calls milestones gates: MERGE, INSTALL, DEMO, HANDOFF. Every story names the gate it's holding up, and "gate distance" means how close a story is to unblocking the next one. You'll see the word in the prompts below and on your GitHub board.

                                                                                          Session open. Type this at the start of every module from Module 6 on:

                                                                                          Read BACKLOG.md and SESSION-NOTE.md. Re-check the live state of any
blocker they mention. Then tell me the top three items by gate distance.

                                                                                          Session close. Type this at the end of every module from Module 6 on:

                                                                                          We're stopping here. Update SESSION-NOTE.md: what's proven, what's
open, the exact next step, and the top three next items.

                                                                                          7. How to read a module

                                                                                          Each module has the same parts:

                                                                                          • What you'll do, and the catch to watch for: the moment this module is about.
                                                                                          • Before you start: tick every box.
                                                                                          • Steps, each with:
                                                                                            • ✅ Check: what a good result looks like.
                                                                                            • ⚠️ If you see…: what to do when it goes differently.
                                                                                          • Log it: one line for your notes. Module 9 counts them.

                                                                                          Who runs each command. Every action in a step starts with a label:

                                                                                          Label What you do Used for
                                                                                          🤖 Claude Type the prompt into Claude Code, or /exit to quit it. Claude runs the commands Routine work: folders, branches, commits, builds. The AI does the typing
                                                                                          ⌨️ You Type the command yourself, in a normal terminal Passwords and sign-ins, starting Claude, the guide and notes folders, the instance, and the few checks that must not go through Claude. One exception for the instance: /prove-it:grade (Module 8) installs through Claude, after asking you to type the alias
                                                                                          🔍 Check Claude runs a check; you read its raw output Checking work. The evidence is what the tool printed, not Claude's summary of it
                                                                                          ✏️ Editor Open the file in your text editor and change it yourself Signatures and allow lines. Allow lines are your decision: Claude may propose or add one, but none goes in unread. You read .gitignore before each commit that changes it
                                                                                          🌐 Browser Use the browser profile the step names Your instance and GitHub

                                                                                          Why the split. The lab's idea is that the AI types and people decide. So Claude does the routine typing. You keep three things: your passwords, your signature, and a few checks done without Claude, so at least one check never depends on the AI's word.

                                                                                          Your log. Keep one file, ~/projects/priority-guard-notes/LOG.md, plus ~/projects/priority-guard-notes/catches.md. Each catch gets one line:

                                                                                          <module> | <what caught it> | <what it caught>

                                                                                          A catch is a real problem the process found and that got fixed, or that changed a decision, before it reached the app. Three things are not catches:

                                                                                          • A check firing on something you planted to test it (like the fake token in Module 5). That's the check working: write it in LOG.md.
                                                                                          • A finding nobody has fixed yet. It counts once the fix is merged.
                                                                                          • A style nit, or a finding that turns out to be wrong.

                                                                                          "What caught it" is one of: prd, consult, research, design, guard, test, review, partner, grade, drill. Keep catches.md to catch lines only, with no headings or blank lines, so Module 9 can count them.

                                                                                          Before the workshop. About 60–90 minutes. Do it at least two days early, so there's time to fix anything that fails.

                                                                                          What you'll do

                                                                                          Install the tools, connect your instance, and pass seven pre-flight checks. On the day there's no time to debug an install, so this module moves every likely problem to before the day.

                                                                                          Why a clean bench matters. A coding agent reads everything it's given: your other plugins, your personal instruction files, your saved logins. For a build you can trust and repeat, it should see only what this lab gives it. If you can, do the whole lab in a separate user account on your computer, so nothing from your day-to-day setup leaks in. If you can't, the checks in step 6 tell you what to look for.

                                                                                          Steps

                                                                                          Step 1 — A ServiceNow developer instance

                                                                                          Why this step: The PDI, your own practice ServiceNow instance, is where the app you build will run. The app works on incidents and business services, so without the demo data there's nothing to test it on.

                                                                                          1. Get a Personal Developer Instance (PDI) from the ServiceNow developer site, if you don't have one.
                                                                                          2. Log in as admin. Open Incident > All and check there are demo incidents.
                                                                                          3. Type cmdb_ci_service.list in the filter navigator and press Enter. Check there are demo business services.

                                                                                          ✅ Check: you can log in as admin, and you can see demo incidents and demo business services.

                                                                                          ⚠️ If you see… no business services: tell your instructor. The lab needs at least three, and your instructor can give you a small set to load.

                                                                                          Step 2 — The tools

                                                                                          Why this step: Every later module uses these five tools. Checking each one prints a version now means a missing install shows up at home, not halfway through a build on the day.

                                                                                          Install each of these, then run the check command:

                                                                                          Tool Install Check
                                                                                          Node.js The version the ServiceNow SDK requires; the SDK's documentation names it node --version
                                                                                          ServiceNow SDK npm install -g @servicenow/sdk now-sdk --version
                                                                                          GitHub CLI From cli.github.com gh --version
                                                                                          git Usually already installed git --version
                                                                                          Claude Code From Anthropic's Claude Code documentation. Your instructor gives the minimum version: it must include the built-in /code-review claude --version

                                                                                          ✅ Check: all five commands print a version.

                                                                                          Step 3 — Sign in

                                                                                          Why this step: Each tool needs its own login before it can act for you. The shared settings file makes your Claude sessions behave like everyone else's. Typing your password only into the SDK, never into Claude, keeps it out of any chat record.

                                                                                          2. This lab guide. Clone it into ~/projects (you need the invite from the README's "What you need"). Using the zip instead? You already have it in ~/projects/agentic-build-lab-guide: skip this item.

                                                                                            ⚠️ If you see… Could not resolve to a Repository: you haven't accepted the invite yet, or you're signed in to a different GitHub account (gh auth status).

                                                                                            Reading the guide: open LAB.html from this folder in your browser, or use the online copy at https://claude.ai/artifact/LLZPgYakMRU9hWxmhughrQ (it's the same guide; your instructor shares the link). The commands still copy files from this folder, so keep the clone either way.

                                                                                          3. Claude Code settings, before the first claude run. The guide ships the settings file ready to use: files/claude-settings.json. It turns off the extras that would make your sessions differ from everyone else's: connectors from your Claude account, saved memories and web search. It also starts Claude in auto mode: Claude goes ahead with routine actions, like writing a file it was asked to write, without stopping to ask you each time, and still checks with you before anything risky.                                                                                             mkdir -p ~/.claude

                                                                                            -n never overwrites: if you already have a settings file, cp leaves it alone (it may print not overwritten, or nothing at all; neither is an error).                                                                                             diff ~/projects/agentic-build-lab-guide/files/claude-settings.json ~/.claude/settings.json && echo "settings in place"

                                                                                          ✅ Check: gh auth status is green. In a normal terminal, not in Claude, now-sdk auth --list shows your alias. Don't show that output to anyone or paste it anywhere: it names your instance.

                                                                                          What you'll do

                                                                                          Real work never starts with a clean brief. It starts with a use case someone wrote, workshop conversations, and technical documents about the customer's systems. Someone turns the first two into a PRD: the requirements everyone agrees to build. The technical documents come in later, when you research the platform (Module 3).

                                                                                          In this module you're handed a PRD, drafted by the platform team from two inputs. Your job is to review it against the inputs, like the person who has to sign it. Then the customer (your instructor) accepts it, and it becomes what the rest of the lab builds from.

                                                                                          Why review, and not just accept it? A PRD is a summary, and summaries drift. It can say something nobody asked for, or quietly drop something somebody did ask for. Both are cheap to fix now and expensive later.

                                                                                          The catch to watch for. Is everything in the PRD backed by an input? Is everything important in the inputs in the PRD?

                                                                                          Module 2 — Consult: understand before building

                                                                                          Day 1 · about 90 minutes · the first stage of five

                                                                                          ← Module 1 · Lab home · Module 3 →

                                                                                          What you'll do

                                                                                          Nothing gets built in this module. That's the point.

                                                                                          The consult reads your accepted PRD (it calls it the brief) the way a sceptical senior engineer would, and answers the architecture questions before any code exists:

                                                                                          • For each of the six capabilities: plain code, an AI skill, or an agent?

                                                                                            • An AI skill is one call to a language model, for when the problem is language.
                                                                                            • An agent decides its own next steps while it runs.

                                                                                          • Which tables and roles the app needs, and which code owns each table.
                                                                                          • What any AI would cost.
                                                                                          • Is the brief ready to build, or does someone need to decide something first?

                                                                                          It leaves one file: CONSULT.md.

                                                                                          The catch to watch for. Read capabilities 2 and 6 in the PRD side by side. One says the priority can never go below the floor. The other asks AI to "adjust the priority". Does the consult notice that these pull against each other?

                                                                                          3. Your PRD

                                                                                          Size it

                                                                                          Why this step: A PRD that's too big makes each review too long to read properly, and things slip through.

                                                                                          The consult reads the whole PRD. If it has more than about 12 capabilities, put one release or epic in brief/, and list the rest under Out of scope as "later releases". A PRD of 40 capabilities makes a consult and a design challenge too long to review properly.

                                                                                          Format it

                                                                                          Why this step: The kit expects this layout, so using it lets every module read your PRD.

                                                                                          • Markdown, one file. Convert a Word or PDF document first.
                                                                                          • Use the layout of the workshop's files/PRD-PriorityGuard.md: Problem, Users, Capabilities requested (numbered, each with "Accepted when"), Non-functional requirements, Out of scope, Success looks like, Open decisions, Acceptance.

                                                                                          Review it (Module 1, on your own inputs)

                                                                                          Why this step: Every line should trace back to something the customer said, so you don't build guesses.

                                                                                          Put your inputs and your PRD in a review folder and run Module 1's steps, with this trace prompt (🤖 Claude, in the review folder):

                                                                                          Trace <your PRD file> against the input files here. For every capability
and requirement in the PRD, quote the input sentence that supports it, or
say "no source". Then list every input statement that changes what gets
built but isn't in the PRD. Quote, don't paraphrase. Don't fix anything,
and don't edit any file.
                                                                                          • There's no answer card. Open decisions go to the real owner, and you wait for their answers. Never answer a business question for them.
                                                                                          • Acceptance is the real owner's name, role, date and signature.
                                                                                          • Copy the accepted PRD into ~/projects/<app>/brief/, as the only file there.

                                                                                          4. Module by module

                                                                                          The steps, commands and safety rules are the workshop's. This section lists every place a module assumes Priority Guard, and what to do instead.

                                                                                          Module 2 — Consult

                                                                                          Why this step: The consult only helps if you push back with your own rules, not the workshop's.

                                                                                          • Step 2: if it asks about size, give your honest estimate for the PRD in brief/.
                                                                                          • Step 2's reply about "contradicts capability 2" is Priority Guard's. Use your own: if a bullet contradicts a rule your PRD states, type Bullet [n] contradicts capability [m]. Correct it.
                                                                                          • Step 4: instead of capabilities 6, 2 and 4, read every row marked AI skill or agent (its reason), the ownership table (one owner per table), every VERIFY item, and the readiness verdict.
                                                                                          • Step 5: for every row marked AI skill or agent, push back: Capability N is marked [AI skill / agent]. Why can't plain code do it? If it can, change it.

                                                                                          NEW · After Module 2 — Choose one slice

                                                                                          Why this step: A small slice you finish beats a big one you don't, and trying the riskiest part first shows early whether the idea holds.

                                                                                          Most real PRDs are 20 to 40 stories. You'll finish one slice: the thinnest piece a real user can use from start to finish. Everything else is deferred, not dropped.

                                                                                          1. 🤖 Claude (~/projects/<app>):
                                                                                            Read brief/ and CONSULT.md. Propose two or three end-to-end slices. Each
slice must: let a real user do one complete thing; be about 5 to 8
stories; use no generative AI; avoid anything the consult marked not
ready or conditional, or listed under Open decisions; and avoid
integrations unless the slice can't work without one. For each, list the
capabilities it covers, what it defers, and the riskiest assumption it
tests. Don't write any file.
                                                                                          2. Choose one. Prefer the slice that tests your riskiest assumption first, not the easiest one. Keep it small now: cutting it later is costly (section 5).
                                                                                          3. ✏️ Editor: write SLICE.md in ~/projects/<app>, by hand: the capabilities in the slice, the ones deferred, the one thing a real user will be able to do, and your live check, the steps an ordinary user follows to see it work.
                                                                                          4. Get the real owner's OK on what's deferred, in writing.

                                                                                          Module 3 — Research and LLD

                                                                                          Why this step: Keeping the research and the LLD (the detailed design) to the slice means you study only what you'll build.

                                                                                          • Step 1: copy your technical documents into ~/projects/<app>/inputs/, not TECH-NOTES.md.
                                                                                          • Step 3: in the research prompt, replace "what a scoped app needs to update incidents" with what a scoped app needs to read and write the tables your slice uses. Add Only the capabilities in SLICE.md.
                                                                                          • Step 5: add Only the capabilities in SLICE.md. In section 1, list every deferred capability as "not built: deferred in SLICE.md".
                                                                                          • Step 6's review checks become:
                                                                                            1. every slice capability is in §1, and every deferred one says so;
                                                                                            2. §3 says where your logic runs and when, backed by the research log;
                                                                                            3. §4 covers who can do what, and the cross-scope access the app needs;
                                                                                            4. §5 has a failure mode for each component;
                                                                                            5. §6 tests your central rule off the instance, and your live check on it;
                                                                                            6. §7 matches what you found.
                                                                                          • Before the LLD goes into the repo (Module 5 step 9), grep it for the customer's name and its instance host names too, not only service-now.

                                                                                          Integrations. If your slice calls another system:

                                                                                          • Credentials go only into a connection and credential record an admin sets up by hand on each instance. Never into src/, into Claude, or into a drill card.
                                                                                          • Keep the outbound call out of your plain-code logic, so that logic still tests in seconds without the instance.
                                                                                          • Each instance (dev, test, production) needs its own endpoint and credential. Note them for PROMOTE.md.

                                                                                          Module 4 — Challenge and sign

                                                                                          Why this step: The signed design is the contract for your slice, so the real owner has to agree to every line.

                                                                                          Use this positions list instead of step 1's. Fill every line from your LLD:

                                                                                          • Feature name: letters only.
                                                                                          • Your design in your own words: three or four sentences from LLD §1–§3, and say what's deferred: "This record covers SLICE.md; capabilities N and M are deferred."
                                                                                          • The central rule: the one rule that, if broken, puts a wrong value on a real record or skips a control. Written as separate short sentences.
                                                                                          • When your logic runs, and what it must survive: LLD §3 and §7.
                                                                                          • Who can change what: each table and setting, from LLD §4.
                                                                                          • What the app must never do: for example, change global behaviour without approval.
                                                                                          • An off switch: an admin-controlled setting that turns off the app's logic. It's required for production (PROMOTE.md §1), so put it in the design now, as a term, with a test.
                                                                                          • Demo data: which seed records show the slice working.
                                                                                          • Deferred: the capabilities in SLICE.md's deferred list.
                                                                                          • Gates: MERGE, INSTALL, DEMO, HANDOFF. DEMO means the real owner sees the slice work, live, as an ordinary user.

                                                                                          When the challenge asks about a deferred capability, answer Out of scope for this record; deferred in SLICE.md. Never answer Not decided: that writes an OPEN term, which fails the grade.

                                                                                          Who signs §9: the real owner, with their name and role. It's their contract. You can't sign it for them.

                                                                                          Module 5 — Fence and plan

                                                                                          Why this step: The safety setup doesn't change, only the names, and the repo belongs to the customer from day one.

                                                                                          Unchanged, apart from your names: workspace, feature, <SCOPE> and <APP_REPO>. Create the repo in the customer's GitHub organisation, for example gh repo create <org>/<repo> --private …. The plan covers only the slice, because the signed design does.

                                                                                          Module 6 — The build loop

                                                                                          Why this step: The loop is the same; these swaps make each check test your rule, not the workshop's.

                                                                                          • Step 2: take whatever is top, always. The floor-story expectations don't apply: expect the bullets to match your central rule.
                                                                                          • Step 4: the example test name becomes one from your central rule.
                                                                                          • Step 8: in the batch prompt, the first Stop when line becomes your slice's key story (the one that wires your logic into the platform), and docs/DESIGN-PriorityGuard.md becomes your design record. When you read that story's pull request, the bullet questions become: when does your logic run, what does it write, and does anything in this story let your central rule be broken?
                                                                                          • Step 10: run your live check from SLICE.md, as your ordinary user.
                                                                                          • Seed your demo data as source in the app (src/). The grade checks for it. PROMOTE.md covers keeping it out of production.

                                                                                          Module 7 — Break it

                                                                                          Why this step: Real users will try things you didn't plan for, so keep looking for holes until a round finds none.

                                                                                          • Step 2: in the reviewer prompt, replace the rule with your central rule, in one sentence. Keep the rest.
                                                                                          • Step 3: don't stop after one fix. On real work, repeat with a new reviewer until a round finds nothing.
                                                                                          • Part B: a colleague who didn't build it attacks your live app, as your ordinary user. Their goal: break your central rule. The attack ideas become: change the record after your logic has run, change related records, save twice, and edit from the list view.

                                                                                          Module 8 — Grade and handoff

                                                                                          Why this step: The grade and the drill show whether someone else could look after your app, which is what the customer needs.

                                                                                          The order changes. See section 5: grade at DEMO, hand off, then grade again at HANDOFF.

                                                                                          • Step 9.2: re-run your live check.
                                                                                          • The drill needs a colleague who plants a failure realistic for your app, while you're out of the room.

                                                                                          Module 9 — What the process caught

                                                                                          Why this step: Writing down what isn't built stops anyone thinking the app is more ready than it is.

                                                                                          Step 3's "not built" list is your SLICE.md deferred list, plus anything the grade or verdict left open. Add one line: what you'll build next.

                                                                                          5. Finishing the slice

                                                                                          The gates, in order

                                                                                          Why this step: The open-story count shows where you really are, so nobody has to guess.

                                                                                          The plan files one milestone per gate: MERGE → INSTALL → DEMO → HANDOFF. The next gate is the one BACKLOG.md names at the top. Count what stands in its way, swapping in its name. 🔍 Check:

                                                                                          Run exactly this and show me the raw output, unedited: gh issue list --state open --label "gate:<next gate>" --limit 5000 --json labels --jq '[.[] | select(all(.labels[]; .name != "register"))] | length'

                                                                                          Keep running the build loop, one story at a time, until it's zero. Then move to the next gate. Nothing closes milestones for you. The count is the truth.

                                                                                          Evidence the grade needs

                                                                                          Why this step: The grade credits only what it can see proof of, so leave the proof where it looks.

                                                                                          • DEMO counts only if the DEMO story is closed with a comment that records who saw what, live, as which user, and when.
                                                                                          • Demo data must be seeded as source in src/.
                                                                                          • Every design term must be named by a test (C<n>: …), including the off switch.

                                                                                          The order to finish

                                                                                          Why this step: Grading before the handoff finds problems while they're still cheap to fix.

                                                                                          1. Close every gate up to and including DEMO.
                                                                                          2. Grade at DEMO, for real. That's Module 8 Part A, with the /permissions you settled at the kick-off. It isn't a preview, because the milestone is reached.
                                                                                          3. The grade files its findings as stories. Some may re-open an earlier gate. Work them until every gate up to DEMO is back to zero.
                                                                                          4. Hand off: Module 8 Parts B and C, including the drill and the verdict.
                                                                                          5. Grade again at HANDOFF. That's the grade PROMOTE.md asks for.

                                                                                          Done means

                                                                                          Why this step: A clear finish line stops the slice dragging on, or being called done too soon.

                                                                                          • ☐ Every gate's count is zero: BACKLOG.md names no next gate.
                                                                                          • ☐ The app is installed on your development instance, and your live check passes as your ordinary user.
                                                                                          • ☐ The DEMO story is closed with the owner's live sign-off recorded.
                                                                                          • ☐ A real grade at HANDOFF, not a preview.
                                                                                          • ☐ HANDOFF.md has a verdict.

                                                                                          Check-ins with your instructor

                                                                                          Why this step: A second pair of eyes spots a stuck slice before a week is lost.

                                                                                          When Bring The question
                                                                                          End of week 1 SLICE.md, the board, your catch list Is the count going down? If it's flat for a week, stop filing and start closing.
                                                                                          End of week 2 Both grades, HANDOFF.md Is it done? What's next: the next slice, or production?

                                                                                          If the slice won't finish

                                                                                          Why this step: Cutting the wrong way loses work or lowers the grade; this way keeps everything on record.

                                                                                          Cut stories, not terms. In the next /prove-it:build-plan preview, mark each cut story as register, keeping its existing key. That takes it off the gates without losing it.

                                                                                          Avoid withdrawing a design term. The kit never deletes terms: a withdrawn term stays in the record, and as far as the kit's documents say, it still needs a test. Without one, the grade is capped at 74. That's why the slice should be small from the start.

                                                                                          6. The next slice

                                                                                          Don't start a new design record. A second design record in the same repo changes how tests must be named, which can stop slice 1's tests counting, and its plan keys need a different prefix. Instead:

                                                                                          1. Save the first consult (CONSULT.md → CONSULT-slice1.md in the workspace) before running anything that rewrites it.
                                                                                          2. Add an LLD addendum for the new slice: research and the same LLD sections, for the new capabilities only.
                                                                                          3. Extend the same design, 🤖 Claude:
                                                                                            /prove-it:design-challenge amend docs/DESIGN-<Feature>.md
                                                                                            The new terms continue the numbering, and the real owner signs the new drift rows.
                                                                                          4. Re-run the build plan for the new stories, then the build loop.
                                                                                          5. Go back to Module 1 only if the PRD changes.

                                                                                          Getting it to production

                                                                                          Lab home · ← Your own PRD track

                                                                                          Everything in this lab runs on a development instance, on purpose. The coding agent never touches test or production, and nothing in the kit does either. Getting a finished app to production goes through the customer's own change process, run by the people who own those instances.

                                                                                          This page is a checklist for that step, not a set of commands. How apps move between instances (an application repository, source control, or something else) is the customer's platform team's decision, and it differs from customer to customer. Several platform behaviours below are marked confirm with your platform team: they're likely, but check them on their instances before you rely on them.

                                                                                          1. The bar before you ask

                                                                                          None of these can be waived.

                                                                                          • ☐ The slice is done, as OWN-PRD.md section 5 defines it: every gate's count is zero, and BACKLOG.md names no next gate.
                                                                                          • ☐ A real grade at HANDOFF, not a preview, in the "ready with named fixes" band (75) or above.
                                                                                          • ☐ No cap on that grade from build, tests or the secrets scan, from a missing signature, or from an unbounded AI feature.
                                                                                          • ☐ HANDOFF.md says READY. NOT READY means someone else couldn't run the app from the runbook. That's not something to accept on paper.
                                                                                          • ☐ The real owner has seen it work live as an ordinary user. The DEMO story is closed with that recorded.
                                                                                          • ☐ The app has an off switch: an admin-controlled setting, in the design as a term, with a test, that turns off the app's logic. And the runbook's Recovery section names it. Plain-code logic is live the moment it's installed. Without a switch, the only way to stop it is to back the whole app out.

                                                                                          What can be accepted: a test-coverage gap or a runbook gap the grade named, if the real owner accepts it in writing. Record it in docs/PROMOTION.md (section 2), with who accepted it, when, and the date it will be closed.

                                                                                          2. Agree how it moves

                                                                                          Meet the customer's platform team before you raise anything, and write their answers in the repo, in docs/PROMOTION.md (admit it with an allow line, as you did for docs/):

                                                                                          1. The delivery mechanism. How a scoped app moves from development to test to production at this customer. Ask them, don't assume.
                                                                                          2. Who installs. On test and production it's their team. Never the coding agent, and ideally not the builder either.
                                                                                          3. Global and shared changes. Anything the app changes outside its own scope: shared tables, global rules. These are in your LLD §2–§3, and usually need their own approval.
                                                                                          4. Cross-scope access. On a development instance the platform may record cross-scope access for you as the app runs. On test and production it may not. Logic that worked on dev then fails. Confirm with your platform team, and make sure every cross-scope privilege the app needs is declared in source (your LLD §4 lists them).
                                                                                          5. Demo data stays out of production. Your seed records are part of the app's source, so they'd install everywhere. Agree how they're excluded from the production install, and confirm it works on test.
                                                                                          6. Per-instance configuration. Role-to-group assignments, setting values, and any integration's endpoint and credential are different on each instance. They're set by an admin, by hand, from the runbook's configuration steps. List them.
                                                                                          7. Back-out. How to remove the app if switching it off isn't enough, and what that costs. Uninstalling a scoped app may delete its tables and the data in them, such as override records or audit rows. Confirm with your platform team. Write the agreed back-out in docs/PROMOTION.md.
                                                                                          8. The version. Bump the app's version in now.config.json, merge it, then tag that commit, so test and production get exactly what was graded:
                                                                                            git tag -a v1.0.0 -m "Slice 1: <what a user can now do>"
git push origin v1.0.0
                                                                                            If anything changes after the HANDOFF grade (runbook fixes, the version bump), grade again at the tagged commit.

                                                                                          3. Test, with the runbook only

                                                                                          1. The platform team installs the tagged version on test, following RUNBOOK.md and nothing else, then does the per-instance configuration (section 2, item 6). If they need to ask you anything, that's a gap in the runbook: fix it through the build loop, re-tag, and start this step again.
                                                                                          2. First contact with real data. Test usually holds copies of real records. Re-run your live check, and the access checks, as ordinary users. Check the cross-scope access works here. Anything that fails goes back through the build loop on development. Never a fix on test.
                                                                                          3. Rehearse Recovery on test. Switch the app off with its off switch, and check it really stops. Then switch it back on. If the platform team allows it, rehearse the agreed back-out too. The handoff drill tested diagnosis, not recovery, so this is new evidence.
                                                                                          4. Re-run the handoff drill on test, if the platform team allows a planted failure there.

                                                                                          ✅ Check: every result is in docs/PROMOTION.md, with dates and who ran it. Nothing was fixed on test by hand.

                                                                                          4. The change request

                                                                                          Raise it through the customer's change process. Attach the evidence. Don't summarise it:

                                                                                          Evidence From
                                                                                          What changes, and what doesn't The signed design record, and LLD §1
                                                                                          How well it's built GRADE.md, graded at the tagged commit
                                                                                          Whether someone else can run it HANDOFF.md and RUNBOOK.md
                                                                                          What was tested on test, and by whom docs/PROMOTION.md
                                                                                          How to switch it off, and how to back it out The runbook's Recovery section, and the back-out in docs/PROMOTION.md, rehearsed on test
                                                                                          Anything accepted rather than fixed docs/PROMOTION.md, with the owner's written acceptance

                                                                                          Say what isn't done. List the deferred capabilities from SLICE.md in the change request itself. Approvers should never discover a gap after go-live.

                                                                                          5. Production

                                                                                          1. Their team installs the same tag from the runbook, without the demo data, then does the per-instance configuration.
                                                                                          2. The off switch starts off. The app is installed, but its logic doesn't run yet.
                                                                                          3. The owner switches it on, at an agreed time, with you available.
                                                                                          4. Watch the first day. Use the checks the runbook gives an on-call person: the platform's own screens, and the app's own lists and logs.
                                                                                          5. If it misbehaves: switch it off first, then diagnose, from the runbook. Back out only if switching it off isn't enough, and only as agreed in docs/PROMOTION.md.

                                                                                          ✅ Done when: it's on in production, the first day's checks are clean and written down, and the owner has signed off in the change request.

                                                                                          6. After go-live

                                                                                          • The next slice extends the same design: see OWN-PRD.md section 6. It goes back through the design challenge before any code.
                                                                                          • Anything found in production becomes a story on the board, built through the loop on development, then promoted with this page again. Never a hand fix in production.
